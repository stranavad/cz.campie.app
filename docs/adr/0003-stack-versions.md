# Stack versions: NestJS 12, Drizzle 1.0 RC, TypeScript 7, Node 26

The stack named in the spec is pinned to the versions below, verified against the npm registry and with working probes on 2026-10-15. Two choices deliberately run ahead of "latest stable": Drizzle stays on the v1 release candidate instead of falling back to 0.45, and the whole repository compiles with TypeScript 7 although the NestJS CLI does not support it yet. Both change how code is written and built, so the rules under Consequences bind every issue.

## Drizzle: 1.0 release candidate, not the 0.45 fallback

The spec names Drizzle v1. It is not stable: 1.0.0-rc.4 shipped on 2026-06-27 with nothing newer since, and the release candidates still contain breaking API changes, while 0.45.4 (2026-10-08) is the latest stable. The developer chose the release candidate, so the project starts on v1's API (relational queries v2, `defineRelations`, the per-migration folder layout, `pgTable.withRLS`) and avoids a migration from 0.45 to 1.0 later in the project. It is pinned exactly because a release candidate may break on any bump. Moving to 1.0.0 stable, once released, is a deliberate upgrade made after reading its release notes.

Drizzle rc.4's own type declarations fail `skipLibCheck: false` with the same 45 errors under TypeScript 6.0.3 and 7.0.2, so this is a Drizzle defect, not a TypeScript 7 one. Our code typechecks cleanly on both.

## Row-level security: Drizzle helpers, not plain SQL

Policies are declared in the Drizzle schema and generated by drizzle-kit:

- Organisation-owned tables are created with `pgTable.withRLS(...)` (`.enableRLS()` is deprecated in v1) and get their policy from one shared helper, so every table carries the same rule: `organisation_id = current_setting('app.organisation_id', true)::uuid`, in both `using` and `withCheck`, for all commands and for the application role.
- The application role is declared as `pgRole('<name>').existing()`, and drizzle-kit runs with `entities: { roles: true }`. Creating roles, their passwords and the grants is done outside drizzle-kit, in a custom SQL migration or in provisioning, because passwords never go into the schema.
- The check that every table has a policy (issue 07) queries `pg_class` and `pg_policies` after migrating, so it does not depend on how policies were declared.

## TypeScript 7 with NestJS

The developer asked for TypeScript 7 provided it works with NestJS. Probes on 2026-10-15, on Node 26.12.0, showed:

- `tsc` 7.0.2 emits `design:paramtypes` and `design:type` metadata correctly with `experimentalDecorators` and `emitDecoratorMetadata`. Constructor injection (also across files), `@Inject` tokens, scopes, pipes and `@nestjs/testing` provider overrides all work, under ES modules with `rewriteRelativeImportExtensions` and `verbatimModuleSyntax`.
- NestJS 12's `StandardSchemaValidationPipe` with Zod 4 validates `@Body`, `@Param` and `@Query`: unknown keys are stripped, defaults and coercion apply, and failures return 400 with path-prefixed messages.
- Vitest 5 runs NestJS tests through Oxc once `oxc.decorator` sets `legacy` and `emitDecoratorMetadata`. Without that it fails to parse decorators.
- Drizzle rc.4 queries, RLS policies and relational queries v2 typecheck on TypeScript 7. Against a real PostgreSQL, an unscoped query saw no rows, each Organisation saw only its own rows, and a cross-Organisation update matched nothing while a cross-Organisation insert was rejected.
- The frontend (Vite 8, React Compiler, TanStack Router and Query, Tailwind 4) builds, and TypeScript 7 rejects wrong route paths, params and search types.
- The NestJS CLI 12.0.8 bundles TypeScript ~6.0.2 and stops with: "The installed TypeScript version (7.0.2) does not expose the programmatic compiler API that the Nest CLI requires. TypeScript 7.0 ships the "tsc" executable only; the compiler API is expected to return in 7.1."
- typescript-eslint 8.71.2 declares `typescript >=4.8.4 <6.1.0`. oxlint's type-aware mode (tsgolint, built on the TypeScript 7 compiler) does work.

## Considered Options

- Drizzle 0.45.4 stable: the spec's own fallback rule, and what Tábor Domino uses (0.44). Rejected by the developer to avoid a 0.45 to 1.0 migration mid-project.
- Plain SQL migrations for RLS: full control, but policies would live apart from the tables they protect.
- Node 24 LTS: proven today, but its support ends about a year earlier than Node 26's.
- TypeScript 6.0.3, which the NestJS CLI supports: keeps the CLI, typescript-eslint and other compiler-API tools, but gives up the native compiler's speed. Kept as the fallback if TypeScript 7 blocks something we need.

## Consequences

- **No NestJS CLI.** `api` builds with `tsc -p` and runs `node dist/main.js`. In development, `tsc --watch` runs next to `node --watch`. There is no `nest generate`; modules are written by hand.
- **API code never runs through esbuild, tsx, ts-node or Node type stripping.** None of them emits decorator metadata. Only `tsc` (build) and Vitest with the Oxc options above (tests) transform `api` code.
- **`api` tsconfig:** `"type": "module"` in `package.json`, `module` and `moduleResolution` set to `nodenext`, `experimentalDecorators`, `emitDecoratorMetadata`, `verbatimModuleSyntax`, `rewriteRelativeImportExtensions`, relative imports written with the `.ts` extension, and `skipLibCheck: true` (required by Drizzle rc.4).
- **Injected classes are value imports.** Oxc emits metadata without type information, so a class used for constructor injection must be imported as a value, never with `import type`. Interfaces and other non-class dependencies are injected through `@Inject(TOKEN)`.
- **Validation is Zod through Standard Schema.** Request schemas live in `packages/schema`. `StandardSchemaValidationPipe` is registered globally, and handlers use `@Body({ schema })`, `@Param('id', { schema })` and `@Query({ schema })` with `z.infer` types. No `nestjs-zod`, class-validator or class-transformer.
- **Lint with oxlint `--type-aware`, format with Prettier.** typescript-eslint is not used.
- **Tools that need the TypeScript compiler API are unavailable** (NestJS CLI, typescript-eslint, ts-jest, ts-morph, the `@nestjs/swagger` CLI plugin). Revisit when TypeScript 7.1 restores the API. If one becomes indispensable before then, the fallback is TypeScript 6.0.3 repository-wide, which reopens this ADR.
- **Drizzle code follows the v1 API:** `drizzle({ client, relations })` with `defineRelations`, and migrations in `drizzle/<timestamp>_<name>/migration.sql`. Code ported from Tábor Domino (0.44) is adapted on the way in.
- **Node 26 everywhere:** `engines`, `.nvmrc`, CI and Docker images.
- Code ported from Tábor Domino that relies on NestJS 11, `nestjs-zod`, React Email 0.5 or ts-jest is adapted to these versions, not kept on the old ones.
